## 1. 引言

### 1.1 目的

定义新闻联播自动化日报系统的功能需求、业务规则、数据需求、非功能需求与验收标准，作为设计、实现、测试与验收的需求基线。

### 1.2 系统定位

一个**无人值守的定时信息生产流水线**：每日自动采集《新闻联播》官方条目，结合检索到的当前形势信息，调用大模型生成结构化政策推演日报，并投递到指定邮箱。核心诉求是**电脑关机也能准时送达**，因此主执行路径部署在云端（GitHub Actions），本地仅用于补跑与调试。

## 2. 系统概述

### 2.1 业务背景

《新闻联播》是政策信号的权威发布渠道。人工每日观看、提取要点、检索背景、形成判断耗时且不可持续。本系统将该流程自动化，并强制输出「可证伪」的分析结论而非情绪化评论。

### 2.2 系统目标

| 编号 | 目标 |
| --- | --- |
| GO-01 | 每日自动产出并投递一份结构化政策推演日报 |
| GO-02 | 全流程无人值守，电脑关机也能送达 |
| GO-03 | 输出可证伪、有边界、有预期差对照，禁止情绪化词汇 |
| GO-04 | 不伪造数据、不编造来源、无数据时如实报告缺失 |

### 2.3 核心链路

```
采集（央视官方API 主通道 + Bing/DDG/Sogou 兜底）
  → 可分析性检查（准入/禁入）
  → 内部五维评分分档（🔴🟡⚪，分数不外露）
  → 形势检索（白名单来源）
  → DeepSeek 分析【逐条计算推演】+【最终判断】
  → 生成主报告
  → 增强板块（连续追踪板/数据口径/政策博弈/待确认追踪/市场流动性）
  → 来源链接有效性核验 + 去分兜底
  → 落盘 reports/YYYY-MM-DD.md
  → SMTP 推送至邮箱（marker 去重）
```

### 2.5 成功标准

| 编号 | 标准 | 判定 | 验证 |
| --- | --- | --- | --- |
| SC-01 | 每个自然日**恰好投递 1 封**日报邮件（不重不漏） | marker 去重 + 延迟发送 | A |
| SC-02 | 当日无数据时**不得伪造**日报，宁可延迟或发「缺失说明」 | 缺失路径 | I |
| SC-03 | 日报中**不出现任何分数**或分项评分数值 | 提示词红线 + 正则兜底 | T（UT-16～UT-18） |
| SC-04 | 预测必须含四要素（时间窗口/核心条件/跟踪指标/证伪条件） | 提示词模板 | I |
| SC-05 | 引用的数据来源必须为可核验的可信 URL | 白名单 + 链接核验 | T（UT-06～UT-11） |
| SC-06 | 全流程 ≤20 分钟 | 工作流超时 | A（实测 389s） |

### 2.7 非目标（Non-Goals）

- 不提供图形界面、Web 服务、移动端
- 不提供用户体系与权限管理（凭据即权限）
- 不做交易日历/休市日特判
- 不做邮件打开/回执追踪
- 不提供投资建议与交易执行
- 不保证日报观点正确，仅保证推理过程可追溯、结论可证伪

### 5.3 详述：UC-01 云端定时生成并投递

| 项 | 内容 |
| --- | --- |
| 前置条件 | 仓库 4 个 Secrets 已配置；当日 marker 不存在 |
| 触发 | cron 到点（北京 21:00 起，每 30 分钟一班，共 5 班） |
| 主流程 | ① 注入 Secrets 与 `TZ` ② 校验 4 个变量 ③ 执行 `standalone_report.py` ④ marker 预检 ⑤ 加载跨日状态 ⑥ 采集 ⑦ 形势检索 ⑧ 主报告 LLM ⑨ 状态回写 ⑩ 市场检索 + 增强板块 ⑪ 装配 ⑫ 核验 + 去分 ⑬ 落盘 ⑭ SMTP 发送 ⑮ 写 marker ⑯ 提交 marker 回仓库 ⑰ 上传 artifact |
| 后置条件 | 邮件送达；marker 入库；`reports/YYYY-MM-DD.md`、`state.json`、`standalone.log` 更新 |
| 异常 | 采集为空且 <23:00 → 落盘缺失说明后**不发送**并正常退出；≥23:00 → 发送缺失说明 |
| 非功能 | 全程 ≤20 分钟；每阶段输出带时间戳日志 |

### 6.2 FR-01 采集当日条目　P0

- **输入**：`report_date`（YYYY-MM-DD）
- **处理**：
  1. **主通道**：调用央视栏目 API `api.cntv.cn/NewVideo/getVideoListByColumn?id=TOPC1451528971114112&n=30&sort=desc&p=1&mode=0&serviceId=tvcctv`，筛选 `title` 含 `YYYYMMDD` 的记录，优先取含 `19:00` 的场次，读 `brief` 字段。失败重试 1 次。
  2. **兜底通道**：仅当主通道未取得文本时，按 12 条固定查询模板检索（附录 B.1），Bing 为主、DDG 兜底、Sogou 再兜底，每查询间隔 0.5s。DDG 失败一次后本批次熔断。
  3. **候选净化**：URL 去参去重；排除地方台（`(北京|上海|…|兵团|深圳)新闻联播`）。
  4. **页面抓取**：前 8 个候选页抓正文（超时 12s），**仅保留含目标日期证据的页面**；抓取失败用搜索摘要兜底。
  5. **条目抽取**：正则提取编号条目，去重键为去空白/括号后前 40 字符；过滤「版权/本网/免责」等页脚噪音。
     > **更正（v3.0）**：v2.0 称该正则可「避免误伤 `1.5亿`」，**经 UT-02 实测证伪**——`"产量达到 1.5亿元规模"` 会被抽出 `['5亿元规模']`。真实防护仅覆盖 `2026.08.29` 这类多位数日期（UT-03 通过），不覆盖 1–2 位整数开头的小数。缺陷详见 **D-13**。
  6. **来源过滤**：仅保留白名单来源；条目数 <8 的页面丢弃；条目集 <2 时用命中日期摘要补充。
- **输出**：`item_sets`（按条目数降序）、`sources`
- **异常**：全部失败 → `item_sets` 为空 → 转 FR-06
- **验证**：AC-02（演示）+ UT-01～UT-05（测试）

### 6.4 FR-03 形势检索　P0

### 6.6 FR-05 LLM 分析与主报告生成　P0

- **处理**：组装 user message → `POST api.deepseek.com/chat/completions`，`temperature=0.3`、`max_tokens=8000`
- **模型降级链**：`deepseek-chat` → `deepseek-v4-flash` → `deepseek-reasoner`，每模型 2 次
- **异常矩阵**：

| 场景 | 处理 |
| --- | --- |
| 401 | 立即终止（不重试） |

| 400/404 | 该模型不可用 → 换下一模型 |
| 其他 HTTP | 等待 5s 重试 |
| 返回空内容 | `max_tokens` 提升至 16000 重试 1 次 |
| 全部失败 | 抛错，非 0 退出，**不发送、不写 marker** |

## 7. 业务规则

### BR-01 可分析性检查（准入/禁入）

- **准入**（任一）：可量化经济影响 / 可追踪行政资源 / 明确产业传导链 / 制度性改革
- **禁入**：纯礼仪性外交（除涉重大贸易协定或技术解禁）、领导人形象宣传、未公开军事细节、无产业变量社会新闻、形式化党内会议程序
- **未通过**：仅一句话概况，归入【程序性信息备忘】，标注「纯信息备案，无分析价值」，禁止深度拆解与臆测

### BR-02 五维评分与分档（分数不外露）

| 维度 | 政策信号 | 产业影响 | 量化指标 | 时效落地 | 新提法 |
| --- | --- | --- | --- | --- | --- |
| 满分 | 30 | 25 | 20 | 15 | 10 |

分档：🔴 重点关注 / 🟡 一般关注 / ⚪ 常规报道（只列标题）。输出中严禁出现任何分数或分项数值。**验证：UT-16～UT-18 + AC-03**

### BR-03 官方用词热力词典

`确保(90) / 切实加快(80) / 大力推动(70) / 推动(60) / 关注(40) / 提及(30)`。🔴 条目须给出用词强度；核心用词权重 <50 者倾向归入「程序性/应付式」。

### BR-04 舆情温度解读

🔴 首条或官媒重点必做：分析发布时点（月末/周末/重大会议前）、版面排位（头条/非头条）、是否配发评论员文章，判定「预期管理」或「动员令」。

### BR-05 形势检索与推演深度

🔴 必做、🟡 简做。对每条检索信息做【计算推演】（量级/路径/节奏，须有数字支撑或明确假设）+【判断】（方向/强度/置信度/风险点），引用 URL。未提供时须写「未获取有效检索信息，推演基于基于公开常识并明确标注假设」，严禁硬凑。

### BR-06 预测四要素

时间窗口 / 核心条件（若…则…）/ 3 个跟踪指标 / 证伪底线。

### BR-07 贝叶斯联动更新

历史状态中相关预测被证伪时按规则调整（示例：PMI≤49.5 证伪 → 以旧换新全年销售额上调 15–20%），并注明「联动调整（因 … 证伪）」。

### BR-08 来源纪律

数据来源**仅引用用户提供的可信 URL**；检索无效时明确标注；严禁编造来源或混入无关站点。**验证：UT-06～UT-11**

### BR-09 红线词与推理边界

禁止「暴涨」「龙头」「重大利好」等非理性词汇；禁止从政策直接跳跃到股价；预测必须可证伪。

### BR-10 白名单/黑名单

见附录 B.3。判定：命中黑名单直接拒绝；否则须命中白名单。「**宁可没有，不要垃圾**」。按需求方要求**不含新浪**（UT-09 已验证）。**

### BR-11 去重规则

| 层级 | 机制 | 验证 |
| --- | --- | --- |
| URL 层 | 去查询串后比对 | I |
| 条目层 | 去空白/括号后前 40 字符作键 | UT-05 |
| 检索层 | 按 URL 去重后截取前 N 条 | I |
| 投递层 | `reports/.sent-YYYY-MM-DD.marker` 存在即跳过（`--force` 可覆盖） | AC-06 |
| 分档层 | 同一条目不得跨档重复 | AC-03 |

### BR-12 时间与时区

业务时区恒为北京时间。cron 以 UTC 表达（北京 = UTC+8），工作流注入 `TZ=Asia/Shanghai`。**验证：UT-21～UT-24（日期锚定）**

### BR-13 缺失即延迟

数据缺失且未到末班（<23:00）→ 不发送、不写 marker，由后续班次重试；仅末班仍缺失才发「缺失说明」。当日已发送 → 后续班次跳过。

### 10.3 缺陷详述（含复现步骤）

#### D-01 来源核验对国内站点必然「未确认」　S2

`verify_report_sources` 用 `urllib` 直接 GET 央视等国内站点，境外 Runner 常被拒/超时，导致来源区常被打上「（核验受限，未确认）」。
**复现**：`python scripts\standalone_report.py --date 2026-09-15 --dry-run` → 日志 `[核验] 失效 0 个、未确认 3 个`。
**建议**：仅在明确 4xx/5xx 时标「失效」；网络异常只记日志、不改写正文。

#### D-02 跨日数据序列键被字符截断撕裂　S1

`dataSeries` 用 `k[:12]` 作键，同一指标因前缀长度不同被拆成不同序列。
**复现**：`python docs\verification\unit_checks.py` → `[复现] D-02 数据序列键被截断撕裂（['碳市场累计成交额（前8月']）`
实测孪生键：`"碳市场累计成交（前8月）"` 与 `"碳市场累计成交额（前8月"`。
**后果**：连续追踪板「近 3 次轨迹」永远取不到历史点，FR-11 核心价值**实际失效**。
**建议**：键归一化（去括号内容 + 全角转半角 + 截断 16 字）+ 别名表 + 迁移脚本。

#### D-03 表格分隔行被误采为数据序列　S2

**复现**：`unit_checks.py` → `[复现] D-03`；或检查 `state.json` 的 `"---"` 键。
**建议**：排除纯 `-`/`:` 行与表头行。

#### D-04 预测四要素解析字段互相污染　S1

日报把三要素写在同一行，抽取用行级贪婪正则。该缺陷由三条独立子断言共同界定：

| 子编号 | 断言 | 实测 |
| --- | --- | --- |
| D-04a | `window` 字段不应含「核心条件」 | ❌ 含（字段污染） |
| D-04b | `cond` 字段不应含「证伪条件」 | ❌ 含（字段污染） |
| D-04c | `title` 不应带序号前缀 `"1. "` | ❌ 带 |

**复现**：`unit_checks.py` → `[复现] D-04a / D-04b / D-04c`。
实测：`window` = `"未来1-2个季度。核心条件：若后续披露通道货运量或投资额同比正增长，则板块景气延"`。
**后果**：回灌给 LLM 的历史状态语义劣化，BR-07 贝叶斯联动建立在脏数据上。
**建议**：四要素规范为独立行（非贪婪 + 行尾锚定），或要求追加机器可读 JSON 块。

#### D-05 缺失说明落盘到正式文件名　S2

`defer_send=True` 时先落盘 `reports/YYYY-MM-DD.md` 再 `return 0`，磁盘上会长期存在一份**看起来像正式日报的文件**。
**建议**：延迟发送时改落到 `.deferred-<date>.md`。

#### D-06 marker 提交竞态可致重复发送　S2

marker 持久化 `git push origin main` 失败被 `|| echo` 吞掉；push 失败将使后续班次读到旧仓库、看不到 marker → **可能发送多次**，违反 SC-01。
**建议**：push 失败显式告警；或改用 Actions Cache / 外部状态存储。

#### D-07 无失败告警通道　S2

Secrets 缺失、连续 5 班无数据、SMTP 认证失败只体现在 Actions 日志中。
**建议**：见 FR-13。

#### D-08 超时预算偏紧　S3

单次实测 389s，工作流超时 20 分钟且 5 班独立；检索退化时耗时可翻倍，末班有被 kill 风险。
**建议**：定义耗时告警阈值与自动降级开关。

#### D-09 状态字段静默截断无标记　S3

`cond[:80]`、`falsify[:120]`、`window[:40]` 静默截断。
**复现**：`unit_checks.py` → `[复现] D-09 window 被静默截断（无省略号且长度达上限）`。
**建议**：截断加省略号。

#### D-10 云端与本地「凭据缺失」行为不一致　S2

| 场景 | 日报是否生成 | 是否发送 | 退出码 |
| --- | --- | --- | --- |
| 云端，任一 Secrets 缺失 | **否**（工作流前置校验步骤直接 `exit 1`，python 从未被调用） | 否 | 1 |
| 本地，`smtp_config.json` 不存在且无 `SMTP_SENDER` | **是**（落盘发生在 `load_config` 之前） | 否 | **3** |
| 本地，配置文件存在但字段为空 | **是** | 否（`[跳过] 配置缺失`） | 0 |

**建议**：统一为 FR-17。

#### D-11 容量显示把字符数标为 KB　S3

`standalone_report.py:1037` 与 `send_report.py:211` 均用 `len(str)/1024`，分母是 1024 但被除数是**字符数**。
**三级口径闭环（v3.0 精确化）**：

| 口径 | 值 | 说明 |
| --- | --- | --- |
| 逻辑字符数（LF） | **10,922** | `len(md)`，即日志计算的输入 |
| 日志显示 | **10.7 KB** | `10,922 ÷ 1024 = 10.67` ✅ 完全吻合 |
| 落盘字符数（含 CRLF） | **11,145** | `10,922 + 223 = 11,145` ✅ 完全吻合 |
| 落盘字节数 | **25,144**（24.6 KB） | UTF-8，中文 3 字节 |
| 低估倍数 | **≈2.30×** | `25,144 ÷ 10,922` |

**复现**：`unit_checks.py` → `[复现] D-11`
**建议**：改用 `len(md.encode("utf-8"))` 或 `out_path.stat().st_size`，并明确单位。

#### D-12 状态文件非原子写 + 行尾符跨平台不一致　S2

1. `save_state` 用 `write_text` 全量覆盖，**非原子**；`load_state` 对解析失败**静默降级为默认骨架**，等于历史清零且无提示。
2. `Path.write_text` 在 Windows 默认 `\n → \r\n`，实测落盘含 **223 组 CRLF**，与云端字节不一致。
**复现**：`unit_checks.py` → `[复现] D-12 ... 共 223 组`
**建议**：临时文件 + `os.replace()`；写入显式 `newline="\n"`。

#### D-13 条目抽取误伤小数　S2【v3.0 新发现】

**现象**：`extract_items` 把「1.5亿」这类小数误判为「条目序号 1. + 正文」，抽出伪条目。

**触发面刻画（实测 10 例，6 例误伤）**：

| 输入 | 输出 | 判定 |
| --- | --- | --- |
| `产量达到 1.5亿元规模` | `['5亿元规模']` | ❌ 误伤 |
| `，1.5亿吨规模` | `['5亿吨规模']` | ❌ 误伤 |
| `增长 2.5个百分点以上` | `['5个百分点以上']` | ❌ 误伤 |
| `占比 3.2万亿元规模` | `['2万亿元规模']` | ❌ 误伤 |
| `约为 12.5%左右水平` | `['5%左右水平']` | ❌ 误伤 |
| `前8个月累计成交 9.8亿吨规模` | `['8亿吨规模']` | ❌ 误伤 |
| `1.5亿吨` | `[]` | ✅ 正常（正文不足 4 字） |
| `2026.08.29 发布` | `[]` | ✅ 正常 |
| `1.推动产业升级` | `['推动产业升级']` | ✅ 正常 |
| `（3）推动产业升级` | `['推动产业升级']` | ✅ 正常 |

**根因**：正则前瞻字符类 `[\u4e00-\u9fff0-9【\[\（(]` **包含 `0-9`**，使「1.」后的数字 `5` 通过了「必须为中文/数字/括号」的守卫；正文长度下限 4 字符，故 `1.5亿吨`（正文 3 字）不触发，`1.5亿元规模`（正文 5 字）触发。

**影响**：`acquire()` 对央视 brief 与页面正文抽取时可能注入伪条目（真实新闻稿中「9.8亿吨」「2.5个百分点」等表述常见），进而：
- 污染 `item_sets` 与条目总数（与官方 24 条口径比对失真）；
- 伪条目可能进入分档分析，产生无意义内容。

**与 v2.0 的关系**：v2.0 在 FR-01 与 SDD M-07 中断言该正则「避免误伤 `1.5亿`」——**该断言错误**，本缺陷即由执行 UT-02 证伪。

**复现**：`python docs\verification\unit_checks.py` → `[FAIL] UT-02`
**建议修复**：前瞻收紧为「不得为数字」，即把 `(?=[\u4e00-\u9fff0-9【\[\（(])` 改为 `(?=[\u4e00-\u9fff【\[\（(])`，或显式排除 `\d` 后紧跟 `.` 的小数形态。详见 SDD DD-15。
